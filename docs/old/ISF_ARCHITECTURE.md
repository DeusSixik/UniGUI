# ISF: архитектура независимых визуальных рецептов

## Главный принцип

ISF-рецепт является не игровым рецептом Minecraft, а независимым документом отображения.
Импорт из RecipeManager, тегов или loot table создаёт начальную копию ISF-документа. После
импорта изменение исходного рецепта не меняет ISF-документ, а изменение ISF-документа не
регистрирует и не модифицирует настоящий игровой рецепт.

## Слои

- `definition` хранит recipe type, recipe, параметры, визуальное дерево и выражения.
- `runtime` разрешает наследование и строит итоговый документ для отображения.
- `trigger` сопоставляет игровые или внешние события с рецептами и открывает их игроку.
- `persistence` хранит открытые рецепты и закладки в данных конкретного мира.
- `importer` создаёт независимые определения из Minecraft и других модов.
- `client` отображает браузер рецептов и в будущем размещает визуальное дерево через UniGUI.

## Наследование

Recipe type может наследовать другой recipe type. Recipe сначала наследует свой type, затем
опциональный родительский recipe и только после этого применяет собственные параметры и visual.
Циклы и отсутствующие родители являются ошибками загрузки, а не молча игнорируются.

## Параметры и будущий Node Editor

Recipe type объявляет типизированные параметры. Recipe задаёт их значения. Свойство визуального
узла хранит либо literal, либо expression. Expression использует именованные операции из реестра
функций и ссылки на параметры, поэтому будущий Node Editor сможет сериализовать граф в тот же
runtime-формат. Например, `percent(energy, maxEnergy)` можно передать в свойство `ProgressBar.value`.

Редактор не должен исполнять произвольный Java-код. Новые функции регистрируются модами через
публичный реестр и получают только типизированный evaluation context.

## Триггеры

Trigger идентифицируется `ResourceLocation`, а не enum. Встроенные id: `isf:craft`, `isf:use` и
`isf:station`. Другие моды могут зарегистрировать новый тип и вызвать его через API, не создавая
compile-time зависимость между ISF и вызывающим модом.

Recipe type сам по себе не отображается: открываемой сущностью является только recipe с хотя бы
одной trigger binding.

## Данные мира

Открытые рецепты и закладки хранятся в `SavedData` мира по UUID игрока. Клиент получает снимок
с сервера. Таким образом, одиночные миры и разные серверы не используют общий файл закладок.

## Генерация

`/isf generateRecipes [selectors]` создаёт независимый datapack мира `datapacks/isf_generated`.
JSON-рецепты находятся в `data/isf/isf/recipes/generated`, а сгенерированные базовые шаблоны —
в `data/<namespace>/isf/recipe_types`. После генерации применяется обычный `/reload`: это
намеренная граница, чтобы запись файлов и замена рабочего registry оставались раздельными
транзакциями. Положительный селектор включает категорию, отрицательный (`-category`) исключает её;
несколько значений разделяются запятыми.

Генератор не читает игровые рецепты после создания файлов. Изменение recipe/datapack другого мода
не меняет уже созданный ISF JSON, а правка ISF JSON не создаёт игровой рецепт. Повторный импорт —
отдельное явное действие администратора.

## Интеграция RecipeType

Интеграционный мод реализует `IsfRecipeTypeSupport` и регистрирует его через
`IsfApi.registerRecipeType(...)`. Реализация предоставляет:

- категорию команды генерации;
- `IsfRecipeTypeDefinition` со схемой параметров и базовым `IsfVisualNode`;
- проверку поддерживаемого игрового `Recipe`;
- копирование значений рецепта в JSON-параметры;
- при необходимости собственные trigger binding.

Команда сериализует definition типа и отдельные recipe-документы. Recipe хранит только значения
параметров и ссылку на type, поэтому базовый визуал не дублируется в каждом файле. Ручной visual в
recipe может переопределить любой узел шаблона по стабильному `id`.

Клиент получает уже разрешённый visual после наследования. `$parameter` и `$function` вычисляются
при построении UniGUI-дерева. Дополнительные безопасные функции регистрируются через
`IsfApi.registerFunction(...)`; произвольный Java-код из JSON не исполняется.

Встроенная интеграция сейчас покрывает shaped, shapeless, smelting, blasting, smoking,
campfire cooking, stonecutting и smithing (transform и trim). Специальные динамические
crafting-рецепты пропускаются с отдельным предупреждением: их результат зависит от содержимого
слотов и не сводится к фиксированной паре входов и результата. Теги и loot tables требуют
отдельных source-adapter контрактов, потому что они не являются объектами Minecraft `Recipe`.

В контейнерных экранах клиент вызывает встроенные триггеры по предмету под курсором:

- `R` вызывает `isf:craft` и показывает рецепты, результатом которых является предмет;
- `U` вызывает `isf:use` и показывает рецепты, где предмет используется как ингредиент;
- `U` одновременно проверяет `isf:station`, поэтому нажатие над верстаком, печью, камнерезом
  или кузнечным столом показывает рецепты соответствующей станции.

Запрос проверяется на сервере. Подходящие документы добавляются в world-scoped библиотеку игрока,
после чего сервер отправляет клиенту только доступные ему рецепты. Поэтому визуальные документы и
правила доступа не требуется доверять клиенту.
