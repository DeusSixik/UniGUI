# Слой токенов темы

Документ фиксирует контракт слоя токенов для UniGUI 2.0. На этом этапе
описывается API и место токенов в резолве стиля. Массовый перевод виджетов и
удаление старых хардкодных значений выполняются отдельными этапами.

## Назначение

Токены дают теме единый набор визуальных значений. Изменение акцентного цвета,
радиуса или размера текста должно менять весь интерфейс через одну настройку,
а не через десятки правил `StylePack`.

Токены отвечают только за визуальные значения. Геометрия конкретного layout,
позиции элементов и поведение контейнеров остаются в `layout(...)` и API
виджетов.

## Контракт `ThemeTokens`

`ThemeTokens` — один неизменяемый снимок, опубликованный темой. После создания
его значения не меняются. Новая тема или редактор темы создаёт новый снимок и
увеличивает версию темы один раз.

Снимок состоит из четырёх групп:

- `ThemeColors` — поверхности, текст, границы, акцент и производные цвета
  состояний;
- `ThemeShapes` — радиусы, толщины границ и другие визуальные формы;
- `ThemeTypography` — семейство шрифта, размеры, насыщенность и межстрочные
  параметры;
- `ThemeSpacing` — визуальные отступы, зазоры и размеры хрома контролов.

Имена групп являются частью публичного API. Конкретные имена токенов должны
быть стабильными и описывать смысл значения (`surface`, `accent`, `radiusMd`,
`controlHeight`), а не место его использования (`buttonBlue`, `treePadding`).

Пример целевого интерфейса:

```java
import dev.sixik.unigui.api.math.MutableColor;

ThemeTokens tokens = ThemeTokens.builder()
        .colors(colors -> colors
                .surface(MutableColor.fromHex("#1E2126"))
                .accent(MutableColor.fromHex("#4A9EFF"))
                .textPrimary(MutableColor.fromHex("#F2F4F7")))
        .shapes(shapes -> shapes.radiusMd(8.0f))
        .typography(typography -> typography.bodySize(14.0f))
        .spacing(spacing -> spacing.controlHeight(36.0f))
        .build();

ui.theme(Theme.fromTokens(tokens));
```

`Theme.fromTokens(tokens)` создаёт минимальную token-only тему. Для сохранения
встроенных состояний контролов и transition-настроек используется
`DefaultTheme.withTokens(tokens)`. Названия builder-методов в примере
предварительные. До реализации они могут уточняться, но четыре группы и
неизменяемый снимок сохраняются.

## Порядок резолва

Для каждого визуального свойства используется один строгий порядок:

1. Явное значение на виджете — значение, заданное пользователем через
   типизированный setter или inline-style.
2. Локальный override виджета — точечная замена значения темы без отключения
   всей темы.
3. Подходящее правило `StylePack` — тип, классы, `styleId` и состояния.
4. Поиск в `ThemeTokens` — значение из соответствующей группы токенов.
5. Жёсткий fallback виджета — последний резерв для обратной совместимости.

Токены не меняют каскад `StylePack`: подходящие правила по-прежнему
применяются в порядке добавления, и последнее правило перекрывает предыдущее.
Токен является источником значения только когда предыдущие слои не задали это
свойство.

Резолв выполняется при инвалидации темы, состояния или override. Рендер читает
готовый снимок и не записывает значения обратно в пользовательские поля.

## Версии и кэширование

Версия `ThemeTokens` входит в `Theme.version()`. Замена снимка токенов должна
создавать одну новую версию темы и инвалидировать зависимые виджеты одним
проходом. Рендер не должен подниматься по цепочке родителей, чтобы узнать,
изменились ли токены.

Локальный override и inline-style имеют собственные версии. Их изменение
инвалидирует только соответствующий виджет и его потомков, если они читают
унаследованное значение.

## Состояния

Состояния остаются в существующем `WidgetState`. Новые состояния ради токенов
не вводятся. Производные значения (`accentHover`, `accentPressed`,
`surfaceDisabled`) вычисляются из базовых токенов и выбираются текущим
состоянием виджета.

Состояние не должно изменять сам снимок токенов. Один и тот же
`ThemeTokens` можно безопасно использовать несколькими UI-деревьями.

## Совместимость

- `StylePack`, XML, селекторы, классы и `styleId` продолжают работать.
- Существующие темы с `put(...)` подключаются через адаптер и не требуют
  немедленной миграции.
- Текущие hardcoded fallback-значения сохраняются до аудита конкретного
  виджета.
- `themeEnabled(false)` не является способом выбора токена. Для единичного
  свойства используется локальный override или явное значение.

## Обязательный пользовательский пример

Реализация слоя токенов считается завершённой только после рабочего примера.
Команда `/unigui style` должна показывать минимум две темы, переключение между
ними и изменение одного токена, видимое на нескольких типах виджетов. В
документации пример должен использовать тот же публичный API, который получает
пользователь, без внутренних вызовов резолвера.

## Реализованный минимум и следующий этап

Минимальные `ThemeTokens` и группы уже подключены как первый слой в
`MutableTheme.styleFor(...)` и `StylePack.resolveStyleFor(...)`. Это не меняет
существующий каскад и оставляет все hardcoded fallback-значения виджетов
совместимыми.

Следующий этап переводит оставшиеся hardcoded значения popup-хрома и размеров
контролов на отдельные token/style keys, затем остальные виджеты по матрице
аудита.
